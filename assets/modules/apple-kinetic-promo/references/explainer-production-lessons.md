# 知识科普视频：素材与清晰度制作规范

来自 2026-09-07 Astra 科普视频的实际返工。用于同类视频制作，不把这次编码参数当作所有项目的固定标准。遵从用户当前要求和已有授权。

## 1. 先确定画面需要，再搜集素材

- 具体事件配原始发布信息，产品介绍配真实界面或官方演示，研究观点配原文/论文/系统卡，抽象机制配可读的原创示意。
- 每个重要段落提前列出：要解释的事情、所需画面、素材来源、选段、画内显示尺寸。
- 按相关性和可验证性选择 X、YouTube、抖音等来源。平台、素材数量或“官方”标签都不能代替清晰度与内容检查。
- 保存来源、日期、原文件与实际采用的局部。用户截图标为用户提供；原创图标明示意；多段来自同一视频时如实计为一个来源的多个选段。

## 2. 素材入库时做一次质量检查

记录图像宽高；视频另记录时长、帧率、编码、码率及是否含音轨。码率仅供排查，不设跨编码器的统一合格线。

优先获取足够清晰的公开原片，不为缩短下载时间而默认限制到720p。检查实际入片区域的文字、边缘和运动状态：高分辨率文件也可能包含失焦、运动模糊、低清屏幕或已经压缩的内容。

像素需求按最终画内区域计算：

`所需可用源像素 = 画内逻辑尺寸 × 输出缩放倍数 × 镜头最大放大倍数`

裁剪时按裁后区域计算。例：1920逻辑画布渲染为3840宽，视频窗口990宽，对应约1980输出像素；2048宽的清楚工作素材足够覆盖该窗口，无需在每个窗口解码完整4K。

小截图不足时依次考虑：更高清原图/重新获取真实截图、降低显示尺寸、选取更合适的资料。提高输出像素或插值放大不能恢复原始文件缺失的细节。若重构信息版式，明确标为整理或示意。

PDF 分开处理：矢量文字和路径可重新渲染；内嵌位图仍受原始像素限制。保留坐标、图例、页码、裁切位置与来源，不把重采样称为新增细节。

## 3. 对齐素材含义与解说

- 每个选段检查头、中、尾；快速蒙太奇或镜头推近时加密检查，必要时播放完整选段。
- 记录 `source_start`、选段时长、成片起止点和片内偏移，避免只核对素材文件名。
- 画面显示哪款软件，就按实际软件命名。多模型对比要说明哪栏属于目标模型。
- 产品演示不能标成内部科研实录；特定任务评估不能扩展成全部科研能力；旧版资料标年份。
- 浏览器连接失败与素材内容错误分别排查。连接失败应说明实际取得素材的途径；不能把公开PDF下载或用户截图报告为成功的 Computer Use 网页截图。遵从工具的连接与停止要求。

## 4. 短样同时检查风格与清晰度

10–15秒短样尽量覆盖实际素材、大标题、小字/字幕、数字人及一次转场。复杂研究图未进入短样时，另外查看该镜头的代表帧。

- 小字从正常字重开始；轻字重只用于在目标观看尺寸下仍清楚的文字。
- 保持一镜一个主要认知任务，使用字号和少量重点色建立顺序。
- 按用户最新偏好，先给左下角数字人留位置，再排字幕、来源和图表。字幕长句与图表图例也要检查。
- 按最终交付尺寸观看短样；缩小拼图用于找布局问题，不能独立作为清晰度通过的依据。
- 利用已确认的风格和已有授权继续制作，避免为内部质量检查反复索取相同确认。

## 5. 控制渲染和转码成本

- 保留高清原文件，从原文件直接生成所需工作片段；避免从多次压缩的中间片反复取材。
- 确定交付分辨率后，让标题、字幕和矢量元素从工程直接渲染。
- 尽量减少有损编码次数；确需分阶段合成时保留高质量中间文件，再做最终交付。此案例使用图形中间文件CRF10、交付CRF14；这只是已跑通的配置，仍以实际画面判断。
- 长视频先评估内存和解码规模；Windows 同时检查物理内存与系统提交余量。单 worker 和低内存模式不能保证整片连续捕获成功。本机从约 10 秒一段起步，每段落盘后释放浏览器和解码资源，必要时将数字人和音频后期合成；其他环境按实测调整段长。
- 分段保留全局时间轴，渲染前明确核心帧范围与重叠检查范围，最终只拼接核心帧。复用前检查工程与素材指纹；失败时保留有效缓存，避免相同配置反复整片重跑。具体步骤见 [分段渲染与恢复](../../narrated-video-workflow/references/chunk-rendering.md)。
- Windows长渲染使用可持续运行的后台进程，隐藏辅助窗口，保存日志与实际PID；完成脚本等待退出并检查产物。启动成功不能作为任务完成依据。
- `Target closed` 或 `write EOF` 只能证明对应环节失败，不能单凭报错断定OOM、工具会话退出或某个唯一根因。
- HyperFrames 渲染副本放在独立目录，避免在入口目录出现第二个带根composition的HTML。修改后检查当前入口，保留场景/媒体ID与时间一致。
- 工程副本若引用共享素材目录，记录依赖；交付的视频文件应能独立播放。不要重跑旧生成器覆盖已调整好的成稿。

## 6. 最终检查按证据分别记录

| 检查 | 能证明的事情 | 不能替代的事情 |
| --- | --- | --- |
| 框架检查 | 运行、布局、对比度等已测项目 | 素材准确、画质清楚、听感自然 |
| 实际导出帧和选段 | 检查过的位置显示和细节情况 | 未查看的所有帧都完美 |
| 完整文件解码 | 文件与流可完整解码 | 已经试听或逐帧检查口型 |
| 实际播放与试听 | 检查过的声音、节奏和同步情况 | 没有听过的全片听感 |

“画面糊”的修复要做同时间、同显示大小对照，同时看素材细节和文字；素材源、字重、压缩同时改变时，不为某一因素编造贡献比例。未经检查，不把问题归因于聊天预览。

保留必要的原始素材限制；记录仍有的警告及其判断依据，不能将“无错误但有已审阅警告”写成“零警告”。

## 7. 每次交付后再补一条有证据的经验

记录用户反馈、发生的问题、证据、修复动作、复验方式及剩余限制。将适用面明确的经验补回本文件，避免重复规则。

2026-09-10 的 222.44 秒口播片，多次长段捕获失败，最终保留有效帧并补齐短段完成交付；同期系统事件记录到提交内存接近耗尽。问题定位和适用边界见 [该次复盘](../../narrated-video-workflow/references/2026-09-10-case.md)。不要将整次任务耗时都称为编码耗时，也不要由此承诺以后固定几分钟完成。

下一次同类项目重点观察：是否在短样阶段发现低清素材、选段描述是否准确、是否因相同问题再次整片返工。当前规范已经固化，后续复用效果尚待下一项目验证。
